07. Server-side Rendering (SSR) / Routers

Can argue for the pros and cons of CDN vs. serving content locally.

CDN

Pros:

  • Det kan hjælpe med at reducere 'load' på din server, så du kan spare noget bandwidth.
  • Det er nemt bare at importere fra et library, eksempelvis slipper jeg for en ekstra mappe i mit workspace pga. jeg bare har importeret water.css, så mit workspace ser lidt mere clean ud i mit VS Code
  • Det kan hjælpe på latency på et større geografisk niveau, hvis jeg nu har en bruger i Bangladesh, så tager det langt tid for kommunikation mellem client-server pga. jeg kun har min ene server i Danmark, hvis jeg nu havde et CDN så har de servere spredt ud over det hele, formodentlig.

Cons:

  • Man gør sig selv afhængig af en tredjepart, min hjemmeside kommer til at se forfærdelig ud hvis water.css serveren går ned. Surely holder den 🙏
  • Der kan være nogle privatlivsproblemer f.eks. ift. GDPR, tror vist nok brugerens IP-adresse bliver sendt med rundt når brugeren besøger min side, f.eks. når de skal hente water.css.

Local

Pros:

  • Man har fuld kontrol over hvilken version man har, så ens app ikke lige pludselig stopper med at fungere pga. tredjeparten ændrede et eller andet. Man kan selvfølgelig også vælge at låse versionen i den URL man henter fra, men så risikerer man modsat at sin version måske ikke bliver understøttet længere.
  • Virker offline for development/test formål

Cons:

  • Man står selv for at holde styr på opdateringer og versionering.
  • Min server kan være geografisk virkelig langt væk fra brugeren, som skaber latency
  • Ens server kan bliver overbelastet, hvis den skal stå for at servere alt selv

Konklusion

Jeg ville nok gøre mest brug af CDN i den forstand i at jeg ville hente eksterne biblioteker. Dette synes jeg giver mest mening i små skoleprojekter, da jeg hverken skal tænke over GDPR, kunder eller noget andet der er afhængigt af min app, hvis tredjeparterne i min app crasher, så har det ikke rigtig nogle andre konsekvenser end at jeg bare lige skal ind og fikse det. Hvis jeg til gengæld stod for noget som en bank f.eks. så ville jeg nok holde så meget som muligt lokalt, både pga. sikkerhed (f.eks. GDPR), men også for server uptime, i den forstand at din uptime kommer til at være afhængig af dine tredjeparters uptime. Tænker næsten at en blanding af begge ting nok er det som bliver brugt i praksis, et CDN man selv har kontrol over som virksomhed.

Understands how synchronous and asynchronous code affects code execution when reading files.

Node kører i 1 tråd. Det betyder at Node kun kan køre 1 ting af gangen i en ens kode. Det knode snippet hernede under er synkront, som betyder at Node ikke kan gøre andet indtil Den givne kode er færdig, i dette eksempel skal den læse filen færdigt. Kode fra templatingEngine.js 


export function readPage(path) {
  return fs.readFileSync(path, "utf-8");
}

Hvis det er asynkront så kan den godt lave andre ting imens, indtil der kommer enten et callback eller et promise fra den asynkrone kode, alt efter hvordan du har skrevet koden.
Jeg kommer her med et eksempel på asynkron vs synkron. 


console.log("1");
fs.readFile("fil.txt", "utf-8", (err, data) => console.log("2"));
console.log("3");

Hvis det er med readFile så bliver det 1, 3, 2.
Hvis det er med readFileSync så bliver det 1, 2, 3.

Understands the arguments for and against SSR vs. CSR when it comes to:

Load Time

  • SSR:
    Brugeren for færdig HTML, så inholdet kan vises med det samme
    Dog kan det også blive tungt for serveren hvis du har SSR på requests,
    men vores bliver renderet 1 gang på server opstart

  • CSR:
    Brugeren skal 'load' alt js selv og bygge siderne op selv.
    Det er til gengæld lettere på vores server.

Resources spent (duration, when and where)

  • SSR:
    Duration - Kommer an på om du har SSR per request eller server opstart.
    When - Per request eller ved server opstart
    Where - På serveren

  • CSR:
    Duration - Kommer an på brugerens computer
    When - Ved hver ny request
    Where - Brugerens browser

SEO

Crawleren er ligesom en bruger, i den forstand at hvis vi har SSR, så slipper crawleren for at skulle hente filer og JS selv, og får bare indholdet færdigt. Det er bedst practice at køre SSR, ifølge google.
Deres egen crawler er rimelig skarp og kan godt klare CSR hjemmesider, men det er ikke alle søgemaskinerns crawlers der er lige så stærke som googles.

CORS

Du kommer udenom CORS problerme ved at bruge SSR direkte eller ved at bruge en proxy i din CSR app, som så vidt jeg kunne google mig til alligevel bare bruger din egen server som en proxy, så den efterligner SSR.
